## ISSUE-001 · 3d skill 的角色卡/场景卡未定义「档位 + 尺寸 + 张数」（连带一处过时口径）

- **状态**：待实现（用户 2026-09-24 明确「先记录，先不修改」）
- **发现于**：统一档位重构（`docs/unified-tier-tool-design.md` P1–P5）之后的走查
- **位置**：
  - `skills/story-short-generator/SKILL.md` STEP 3 角色卡（L152–177）、STEP 4 场景卡（L178–195）、工具表 L29
  - 口径过时点：同文件 L47（i2i「尺寸跟随参考图（≤1MP）」）

### 现状取证

技能里**已定义**的：查库/复用（`asset_list` → `asset_to_canvas`，未命中才新建）、生成工具（`comfy_generate_image`）、形态硬约束（**角色卡双版本：每个角色出单视图 + 三视图；视频引用按档位选（`fast` 单视图 / `balanced`·`quality` 三视图），非 fast 形态问题先退回单视图**（2026-10-21 起）/ 背景纯净 / 图内零文字 / 不临时拼图 / 不同着装分建状态卡 / 记录 seed 供同 seed 重出 / 带风格锁后缀）、画布分组（`character cards` / `scene cards`）。

技能里**未定义**的：**档位、显式宽高、张数**。

⇒ 实际执行时走工具缺省：`tier=quality`（`DEFAULT_TIER`）、尺寸 = 画布 `aspectRatio` × 该档长边 **2048**（snap32）、`count=1`。

实测/推算尺寸与成本（本机单卡 · Qwen-Image 2.1 int8 · 40 步）：

| 档位 | 长边 | 16:9 | 9:16 | 1:1 | 成本 |
|---|---|---|---|---|---|
| `quality`（**当前缺省**） | 2048 | 2048×1152 | 1152×2048 | 2048×2048 | 4.19MP 实测 **63.4s**；2.36MP 未实测，按像素量估 ≈35s |
| `balanced` | 1344 | 1344×768 | 768×1344 | 1344×1344 | 1.03MP，清单标 ≈5s |
| `fast` | 1024 | 1024×576 | 576×1024 | 1024×1024 | 实测 **~4s**（576×1024） |

（视频侧不受此问题影响：STEP 0 / STEP 7 已要求**逐镜显式传 `tier=`**，长边 832/1344/1344，不许依赖缺省。）

### 影响

1. **成本集中在卡片阶段**：单张卡 40–63s，而技能又要求「自检不过 → 复用同 seed 重出」+ 同一角色多状态卡 ⇒ 一个短剧项目几十张卡、每张可能重出 2–3 次。
2. ✅ **画幅不合适** —— **已修（2026-10-08）**：`story-short-generator` 的资产目录规定**角色卡用 2:3 竖版并显式传 `width`/`height`、不继承影片比例**（`fast` 672×1024 · `balanced` 896×1344 · `quality` 1344×2016）；**道具卡用 1:1**；**场景卡保持影片比例**（它要直接当镜头参考）。实测 `balanced` 896×1344 的卡人物占比明显变大。⚠️ 竖版卡对视频模型 `ref_nodes` 的副作用**未实测**——需确认不会把成片构图往竖版带。
3. **抽卡语义缺失**：`count=1` 等于「一张定生死」，与「抽卡 → 人工选 → 锁定」的流程不匹配。
4. **口径过时（L47）**：i2i 仍写「尺寸跟随参考图（≤1MP）」。统一档位后参考图预算是按档给的（`fast 768 / balanced 1056 / quality 2048`）⇒ quality 档实际是 **2K 级改绘**，与文档描述不符。

### 待定方案（等拍板后实施）

1. **卡片档位分两段**：抽卡迭代（构图/姿态/风格试）用 `tier='fast'`（~4s）；人工选定后**定稿重出**用 `tier='quality'`（卡面细节最实，喂给视频当 `ref_nodes` 更稳）；`balanced` 用于「要快但要能看」的取舍。
2. ✅ **卡片画幅显式指定、不继承影片比例**（已采纳并落地，2026-10-08）：角色卡 2:3 竖版（`fast` 672×1024 · `balanced` 896×1344 · `quality` 1344×2016）；道具卡 1:1；场景卡与影片同比例。落点：`references/asset-catalog.md`（各类资产的「比例」行）+ `SKILL.md` STEP 3。
3. **抽卡张数写死**：每张卡先出 `count=2` 供人选。
4. **同步修正 L47**：把 `≤1MP` 改成按档位预算的口径，并写明 i2i 的 `tier` 决定改绘清晰度上限。

### 影响面

仅技能文档（可选：把上面的「卡片建议」一并写进 `comfy_generate_image` 的工具描述）。**不涉及 runner / manifest 改动**——档位、尺寸推导、i2i 参考图预算注入点都已在 P1–P4 具备。

## ISSUE-002 · 角色卡「先三视图 → 裁正面当单视图」的剩余未知（视频层未实测）

- **状态**：已实现（2026-10-27），但**视频层收益未实测**，附带 3 个已知代价
- **位置**：`workflows/image-crop.json`、`lib/index.js`（`computeCropRect` / `runCrop` / `image_crop`）、`skills/story-short-generator/SKILL.md` STEP 3

### 背景与已取证

角色卡两版（单视图 + 三视图）原先各自文生图，靠「同一份设定文本 + 同 seed + 风格锁 + 跨版本并排自检」兜一致性。实测这对组合**不保证跨画幅一致**：`绛珠` 的 2:3 单视图与 16:9 三视图并排核对时，三视图正面格多了编发冠、发饰与单视图不同。

替代路径（已实现）：**先出三视图（16:9、1×3），再用 `image_crop(panel=0, panels=3)` 裁正面格当单视图**——裁切是纯像素操作，两版同源，一致性按构造成立。

- 真机验证（`scripts/e2e-crop.mjs`）：2048×1152 三视图 → 正面格 **682×1152**，画布配对双向、复用 nodeId 重裁不堆节点；裁切本身 ≈0.1–0.2s。
- 尺寸：三视图 `fast` 1024×576 / `balanced` 1344×768 / `quality` 2048×1152；单视图 = 面板 `341×576` / `448×768` / `682×1152`（比例 ≈0.59，不再是 2:3）。

### 已知代价（不阻塞，登记待观察）

1. **单视图分辨率降到整张的 1/3**：`quality` 0.79MP（旧 2:3 独立单视图 2.71MP，低 3.4×），`balanced` 仅 0.34MP。⚠️ **喂 H3 `ref_nodes` 时这算不算够用未实测**——H3 侧本来会把参考图重采样到采样尺寸，理论上够，但目前没有任何对照组（同角色：裁切单视图 vs 2:3 独立单视图，同 prompt / seed 各跑一条 r2v）。
2. **裁切可能带进旁格内容**：面板边界固定按 `floor(宽/3)` 均分，若三视图里侧面格的头发 / 衣袖越过 1/3 线，会出现在单视图右缘。自检里已加「左右边缘无相邻格残留」一项，但**没有自动检测**（靠人/模型看图）。
3. **单视图不能单独修**：三视图一格画坏（脚被切、背面画错）⇒ 单视图一起废，只能重出三视图再重裁。相比独立生成，这是**修复粒度变粗**的代价，换来的是身份确定性。

### 已试过但**未采纳**的另一条路（记录证据，避免重复试）

「单视图 → 补宽到 16:9（人物放左 1/3、其余纯灰）→ `image.image2image` 生成三视图」：实测可行（正面格几乎是原卡复刻，`quality` 档），但

- 侧面 / 背面两格是**新生成**的，会自创配饰（实测给角色加了金色发冠 / 步摇）；
- 产出物带白色分栏缝（prompt 里"格间留白"被模型理解成白边框）；
- 需要额外一个「补宽 / outpaint」能力（当前没有），链路更长。

⇒ 该路线只在「已有单视图、想补三视图」的场景有价值，暂不实现对外的工具。若要支持，落点是新增 `image.outpaint`（参考图 + 显式画布尺寸，先把参考图 contain 进目标画布再走 ReferenceLatent）。

### 影响面

技能文档与一个新增能力/工具；`image.text2image` / `image.image2image` 的清单与 runner 未改动（`image.crop` 是独立能力，未分档）。存量资产（2:3 单视图 + 16:9 三视图分别生成）**继续合法可用**，不强制迁移。
