# 2K 路径能不能叠 Sol / PDD？——理论分析

> 结论速览：**PDD 可以做，而且它是理论上最贴合的加速器**（pass 2 正是「训练网格上的部分去噪」）。
> **Sol-Attn 现在不能做**：不是理论不行，而是它在 2K 上收益最大、崩服务风险也最大，且现有 sol 配置在 pass 2 上调错了方向。
> 相关：`docs/learned-latent-upscale-2k.md`（2K 路线本体）· `docs/minimax-h3-acceleration-lora.md` §9.9 / §9.10（加速实测与崩溃记录）

## 0. 先把 2K 的开销结构算清楚（这决定了「加速该加在哪」）

H3 的 transformer 序列长度（开放版只有 full attention，稀疏注意力未发布）：

```
S ≈ (W/32) × (H/32) × (frames/4)  +  prefix
```

| 配置 | 视频 token | 备注 |
|---|---|---|
| 原生 1344×768 · 124 帧 | 42×24×31 = **31,248** | + prefix ≈ 6.6k ⇒ **S≈37.8k**（与 §9.10 崩溃日志的 `S=37836` 吻合） |
| 2K 2688×1536 · 124 帧 | 84×48×31 = **124,992** | 换算后 ≈ **3.5×** 原生 |

> 勘误：`docs/learned-latent-upscale-2k.md` 里「精修在 ≈500k token 上跑」说的是 **16× VAE 的 latent cell 数**
> （168×96×31 = 499,968），不是 transformer 的序列长度。真正进注意力的约 125k。

**关键推论**：pass 2 的序列是 pass 1 的 4×（两轴各 2×），而注意力开销随 S 超线性增长。
所以 **2K 的耗时几乎全部由 pass 2 决定**，加速只有加在 pass 2 上才有意义。

按「每步开销 ∝ S^α」建模（α=1 为带宽受限、α=2 为 FLOP 受限，实际介于两者之间）：

| α | pass2/pass1 单步 | 20步 + 6步 配置下 pass 2 占比 |
|---|---|---|
| 1（线性） | 4× | 24/(20+24) = **55%** |
| 2（平方） | 16× | 96/(20+96) = **83%** |

⇒ 两个加速器的作用点都是 pass 2，但**代价与收益的形状完全不同**，下面分开推。

## 1. PDD：理论上是「正解」，因为节点本来就为这个场景设计

### 1.1 结构性契合：pass 2 就是「trained grid 上的 partial denoise」

`MiniMaxH3PDDAccScheduler` 的 `denoise` 参数说明原文：

> *"Keep only the last round(steps\*denoise) blocks (**v2v-style partial denoise on the trained grid**)."*

我们现在用 `BasicScheduler(steps=6, denoise=0.3)` 在 **base 20 步模型**上搭的 pass 2 调度，
有一个 **drop-in 的 PDD 对应物**：`nfe=8, denoise=0.3` → `round(8×0.3)=2` 个 block。
它落在**训练网格上**，所以 `on_off_grid='error'`（fail-closed）不会误触发。
这不是 hack，是节点文档化的模式。

旁证：`MiniMaxH3PDDAccWarmupScheduler`（两段式）的 `handoff_sigma` 选项明确写着
`0.8 → 2 PDD evals`——「base 模型跑到 σ=0.8，再让 PDD 用 2 次评估收尾」，与我们 `denoise≈0.3` 的形状是同一个东西。
说明上游认为「在部分 σ 上进入 PDD」是受支持的模式。

### 1.2 画质方向一致：PDD 的特征正是 pass 2 想要的

§9.9 的实测（1344×768 全去噪）：

| | 细节量（相对成片档 20 步） | 噪声地板 |
|---|---|---|
| PDD nfe=8（ref2v） | **+10.3%**（7.986） | **更低**（0.077） |
| PDD nfe=8（i2v） | **+7.9%**（8.778） | 更低（0.403） |
| lightx2v 8 步（ref2v 侧） | −22%（过平滑） | — |

**「高频更多 + 噪声地板更低」= 多出来的是细节不是颗粒**——这与 2K 路径实测的指纹
（[0.25,0.5] 频带 6.6–7.0×、高频残差 −0.1%）是同一个签名。两者瞄准的目标一致。

### 1.3 成本：换 NFE，不换内核 ⇒ 省时间且不碰崩点

PDD 减少的是**评估次数**（6 → 2），变压器前向本身不变（同样 token、同样显存峰值）。
所以它**不改动 attention 内核、不引入新的分配路径**——绕开了 §9.10 那个 `cuMemFreeAsync` 崩点。

在同一模型上估算整段 2K 的收益：

| 假设 | 现在（6 步 base） | PDD pass 2（2 次评估） | 加速 |
|---|---|---|---|
| α=1 | 20 + 24 = 44 单位 | 20 + 8 = 28 单位 | **1.57×** |
| α=2 | 20 + 96 = 116 单位 | 20 + 32 = 52 单位 | **2.23×** |

即 **2K 全长渲染大概能压到 1.6×–2.2×**（56 帧探针 269.3s 的对应配置下，粗估 6 步版本约 460s → PDD 约 210–290s）。
量级层面这远大于 Sol 的 1.27×，因为 Sol 只改**每步单价**，PDD 改**步数**。
（且这还没算 pass 1 若也换 PDD 的 20→8。）

### 1.4 但有三个真实的理论反对意见

**① 入口在蒸馏轨迹之外（最重要）。**
PDD 是*蒸馏*：它的 8 次评估被训练成一个自洽轨迹，第 k 次评估的输入状态来自第 k−1 次的输出。
而我们的 pass 2 入口状态 = **未蒸馏的 20 步 base 模型输出 + 学习式放大器的重建结果**——
噪声等级与状态统计都对蒸馏轨迹是**域外**的。
节点守住了 *σ 网格*（`on_off_grid`）和 *trunk 族*（`partition_check` 指纹守卫），
但**没有任何机制守住状态分布**。

形式化：蒸馏给的是映射 `F_θ: (x_σ, σ) → x_σ'`，只在训练流形上有效。域外误差理论上无界、实践上未知。
§1.1 的 WarmupScheduler 说明「部分 σ 进入」是设计内用法，但那是**同一条连续轨迹内**的交接，
不是在「放大 + 一步大跳」之后进入。这一条只能靠实测回答，不能靠推理。

**② 块粒度 vs. 时间一致性。**
每个 PDD block 覆盖 4 个 fine step 的 σ 区间，是**大步长**。2 次评估意味着**没有迭代纠错**：
第一次过冲/不足会直接传给第二次。少步蒸馏采样器在「精修」任务上的典型失效模式就是
**过冲 → 闪烁**。而 2K 路径在 denoise 0.35 下已经背着 **+20.9% 闪烁**的代价（base 模型），
PDD 更可能把它推高而不是压低。
⇒ 若做 PDD 变体，**必须把「闪烁」当第一验收指标**，不能只看锐度。

**③ `denoise` 被量化到 1/8 粒度，调参空间变粗。**
`blocks = round(8·d)` ⇒ d∈(0.19,0.31]→2、（0.31,0.44]→3、（0.44,0.56]→4。
你现在能做的「6 步 × denoise 0.3」这种细调不存在了，只有 {2,3,4} 档。
可用带宽与实测最优区间（0.2–0.4）大致重合，但**每个旋钮的量子更大**，容错更小。

### 1.5 合成约束（会限制设计空间）

- **不能与任何其它蒸馏 LoRA 叠加**（lightx2v 系必须摘掉）、不能叠 step-caching。
  2K 路径 pass 1 目前是**无 LoRA 的 20 步 base**，所以无冲突 ✓
- 权重必须与 UNet 同族：2K 的 ref2v 用 ref2va、i2v 用 fl2va，两个 PDD 文件本机都有 ✓
- 音频：`lock_audio=true` 把音频 mask 出 pass 2，所以 PDD 的 audio head 在 pass 2 不被触发；
  但 head bank 会改同一个 model 对象，**pass 1 的音频仍受 PDD 影响**——不能假设音频不受扰动。

### 1.6 因此推荐的落地顺序

**变体 A（先做）：PDD 只加在 pass 2。**
```
SigmaShift(2) ─┬─→ 首遍 sampler（base 20 步，不动）
               └─→ PDDAccApply(2a) ─→ RefineHandoff.model   ← 只喂精修
                                        RefineHandoff.sigmas ← PDDAccScheduler(nfe=8, denoise≈0.3)
```
`RefineHandoff.model` 与首遍 sampler 的 model 是**两个独立输入**——这正是「PDD 只进 pass 2」的干净挂点。
理由是理论上的：pass 1 是运动/构图/音轨的来源，且它本来就便宜，扰动它没有收益只有风险。

**变体 B（A 实测通过后再做）：PDD 同时进 pass 1。**
收益是 20→8（2.5×），但会改掉：
① pass 1 的 latent 统计（**学习式放大器的训练分布也随之变化**，风险不可估）；
② 口型/对白（PDD 的 audio head 生效）。
而且 2K 路径的 `denoise=0.3` 是在「20 步干净 pass 1」上调出来的，换 pass 1 等于作废这套调参。
⇒ 必须分阶段，不能一次改两处。

## 2. Sol-Attn：理论上是 2K 上收益最大的那个，但现在绝不能做

### 2.1 收益侧：Sol 的增益随序列长度单调上升，2K 正是它的主场

节点的 `min_seq_len`（默认 8192）的说明就是 *"Sol-Attn only wins on long sequences"*。
本仓库自己的实测把这条曲线画出来了：

| 分辨率 | 加速 | 高频细节 |
|---|---|---|
| 480p | **1.03×** | **−13.8%**（变软，明确不建议开） |
| 768p（S≈37.8k） | **1.27×** | ±2.5%（持平） |

2K 的 S 是 768p 的 **3.5×**（≈131.6k），且崩溃日志显示 S=37836 时 `density=0.202`——
序列越长，路由越稀疏、跳过越多。**外推下来 2K 上 Sol 的加速很可能明显超过 1.27×**。
这是真实的、值得等的收益。

### 2.2 但风险侧更糟，而且是**不对称**的

§9.10：ComfyUI 0.35.2 + `cudaMallocAsync` 下，Sol 让进程 abort（`cuMemFreeAsync → CUDA_ERROR_INVALID_VALUE`），
**容器整机重启、同机其他人的任务一起被打掉**，复现两次（带续接 / 不带续接都崩，13.7s 内）。
崩点在 Sol 自己的 attention / `torch.compile` 分配路径上。

2K 让这一条**更危险而不是更安全**：分配次数与单次大小随 S 上升（KV 分块打分缓冲 ~O(S)），
整体显存水位也更高。**收益不确定、代价是「崩掉整台共享服务」——这个赌注不成立。**

而且所有 `-sol` 清单当前已声明不可用，意味着**没有可工作的参照物**可以从它出发做变体。

### 2.3 就算分配器问题解决，现有 sol 配置在 pass 2 上也是**调错方向**的

看现有 sol 清单的实际参数：

```
SolAttnMiniMaxH3: dense_first_percent=0, dense_first_blocks=2,
                  approx_correction=true, end_percent 未设 ⇒ 默认 1.0（永不回到稠密）
```

节点自己的 tooltip 说得很直白：

> *"end_percent … Try 0.9: **the last steps set fine detail, where routing error is most visible**."*

现有配置把 `end_percent` 留在 1.0，也就是**最后几步也是近似注意力**。
在 20 步全轨迹上这可以接受（实测高频 ±2.5%）。但 **pass 2 的 6 步，全部任务就是「定细节」**——
近似它们等于直接攻击你花 6.6× 频带能量买来的那个细节增益。

⇒ 2K 的 sol 变体必须**重新调**，而且是往更保守的方向：
`morton=true`（Z-order 让每个 128-token 块成为紧凑 3D 邻域，同样 tau 下路由准得多）、
`end_percent` 明显低于 1.0、tau 调低。这是**一轮新的调参**，而且几乎没有犯错的余量。

### 2.4 还有一个没人验证过的语义问题

`dense_first_percent` / `end_percent` 是「去噪过程的分数」。Sol 是加在 node 2 上的 model patch，
而 node 2 **同时喂**首遍 sampler 和 `RefineHandoff.model`。于是：
这两个分数是**按每次采样运行**各自计数（pass 2 有自己的 6 步窗口），
还是**绑定外层 σ 调度**？

如果是后者，pass 2 那段被截断的调度（σ 0.3→0）会**整体落在 window 之外**，
`dense/approx` 的切换会**静默反向**——你以为最后几步是稠密的，实际全是近似的。
**这一点从节点的声明接口看不出来，需要一次带日志的仪表化运行才能确认。**
（`log_every` 参数说明里确实会打印密度，是可行的验证口子。）

### 2.5 处置

**现在不做。** 触发条件：容器分配器换回原生 caching allocator（去掉
`PYTORCH_CUDA_ALLOC_CONF=backend:cudaMallocAsync` 或设 `backend:native`）并**同 seed 单镜验证通过**之后，
再按 §2.3 + §2.4 重新调一版。在那之前，Sol 在 2K 上属于「已知会崩且配置不对」。

> **执行结果已出**：变体 A 已落地并实测，结论见 **`docs/2k-pdd-ab-verdict.md`**。
> 一句话：全长 **1.86×**（415.3s → 223.8s，56 帧 2K），二遍段 **2.91×**，
> 闪烁 6.645 → 6.595（**未退化**），音轨 PCM 逐样本相同。§4 列的契约改动已按此实现。

## 3. 一句话结论

| | 理论收益（2K 全长） | 风险 | 结论 |
|---|---|---|---|
| **PDD 进 pass 2** | **1.6×–2.2×**（换 NFE，量级 > Sol） | 域外入口 / 闪烁 / 粗粒度调参——**可通过 A/B 量化** | **做**，第一验收指标是闪烁而非锐度 → **实测 1.86×，闪烁未退化** |
| PDD 进 pass 1 | 再 2.5×（pass 1 部分） | 改 latent 统计 ⇒ 放大器分布外 + 口型 | 变体 A 通过后再评估 |
| Sol 进 pass 2 | 可能 > 1.27×（S 长 3.5×） | **崩整台共享服务**（已复现两次）+ 需要重调 + 语义未验证 | **不做**，等容器分配器解决 |

补充：PDD + Sol 组合在 768p 实测是 137.3s（对 20 步 2.9×）——理论上是两者兼得的最优解，
但**共享同一个崩点**，所以同样搁置。

## 4. 若要落地 PDD 变体，契约上要动的地方

1. **参数面**：不能用 `params.steps2`（PDD 的步数由 `round(nfe × denoise)` 决定，且只接受 block 4/8）。
   新参数应为 `pdd_nfe`（8/4/6）+ `pdd_denoise`（步数 = round(nfe×denoise) ∈ {2,3,4}）。
2. **图**：新增 `2a = MiniMaxH3PDDAccApply`（pdd_file 走 `$assets.pdd`）、
   `9b = MiniMaxH3PDDAccScheduler`，`17.model` 指向 `2a`、`17.sigmas` 指向 `9b`。
   首遍 sampler 仍吃 node 2（base），**两条 model 分支**。
3. **requiresNodes** 增加 `MiniMaxH3PDDAccApply`、`MiniMaxH3PDDAccScheduler`。
4. **assets** 增加 `pdd` 槽（ref2v → `h3PddRef2v`、i2v → `h3PddFl2v`，`kind: other`）。
5. **验收判据**（顺序不能换）：
   ① `on_off_grid`/`partition_check` 不报错 ⇒ 调度真在训练网格上；
   ② 闪烁（相对时间中值偏离）不高于 base 6 步版本；
   ③ 锐度/频带不下滑（否则失去 2K 的意义）；
   ④ 若有条件，用 `PDDAccApply.sigmas` 与 `PDDAccScheduler` 输出比对 σ 向量是否同网格。
