## 0. 一句话结论

- **单片路径的人工门密度过高、且前期集中爆发**：任何产物生成之前要先过 **13 张卡**（门 0 + 复用范围 + 11 项生产规格，`SSG:194`/`SSG:224`/`SSG:228-269`），全流程 **≈28 次（batch）/ ≈38 次（per-shot）**。
- **连续短剧路径把门砍到 3–6 次/集，但砍出了洞**：`SSG:213`「跳过本 skill 的 STEP 1/2 与其余 STEP 0 选项卡」+ `PROD:230`「不许再向用户逐项问十项」+ 预填表缺项 ⇒ **声线方案这道「有对白时必须作答」的硬门控被系统性吞掉**（`SSG:13`/`SSG:233-239` vs `PACK:170-183`），`reviewMode`/`groupOrder` 则「有值但没落地到每集会话」。
- **最值得动的三处**：STEP 0 十一项合成一张卡；卡片锁定三类门合一张「资产总览」；门 2 + 分镜模式 + 分镜批准 + 渲染参数卡四连合成两张。

## 3. 触达次数估算

### 3.1 计数方法与假设（必须先读）

1. **1 次「人工触达」= 1 张 `ask_user_question` 选项卡**（含批量卡、求助门、门禁卡）。纯人工操作（入库/上传/通读）**不计入**，在 §2.4 单列；飞书群聊审批卡不计入，另按 ×2 说明（`SSG:921`）。
2. **基准场景 S1（单片）**：45s / 10 镜 / 2 个物理场景（1 个转场镜）/ 2 个说话角色 / 1 张道具卡 / 资产库非空 / 有对白 / 1 角色多状态卡不建 / batch 模式。
3. **基准场景 S2（单片 per-shot）**：同 S1，仅把门 3 从 1 张批量卡换成「每片段 1 张」= 10 正片 + 1 转场 = **11 张**（`SSG:793`：「转场镜同样逐个走本门」）。
4. **基准场景 S3（单集连续短剧）**：90s / 18 镜 / 2 个物理场景（1 个转场镜，`PROD:59`）/ 14–16 对白镜（`PACK:148`）/ 本集不缺卡 / batch 模式。per-shot 时门 3 = 18+1 = **19 张**（`PROD:244` 锁 batch，但 state 可改）。
5. **两套读法**（连续短剧每集到底几道门，文档自身有两种说法）：
   - **「runbook 清单读法」**：`RUN:46-104` + `PROD:236-246` 显式列出的只有 **门 1（镜头表）→ 分镜批准（RUN 称「门 2」）→ 门 3 batch**，交付段（`RUN:96-104`）**没有选项卡**。
   - **「最严读法」**：`PROD:234`「STEP 5.5–8 **完全照执行**」⇒ 还要加 SSG 的 **门 2 自检批准卡**（`SSG:572`）、**渲染参数卡**（`SSG:688`）、**交付批准卡**（`SSG:926`）。
   - 本文**主数字取最严读法**（因为它是「完全照执行」的字面结果，也是用户实际会遇到的），括号内给 runbook 读法。
6. **EP01 样片集**：从零到 G-SAMPLE 批准，含「立项 + 前 10 集剧本（只到 EP01 可用）+ 资产锁定 + EP01 单集生产 + 样片评审」。不含 `/export`（样片阶段不必导出）、不含 O-6 的 30–50 次入库点击、不含每 5 集抽查。
7. **不计**：设置页改档位/换实现、门禁外的 prompt 编辑、写提示词库、`video_upscale` 执行本身。

- 后果：每集新会话若严格照 §8.1 执行，`reviewMode` 读不到 ⇒ **按 per-shot 走 ⇒ 每集从 6 门变成 24 门**（§3.3）。这是「预填值存在但没人写」的典型落地断点。
- 建议：`PROD:8.1` 第 3 步后插入「`canvas_set_state`（按 §1 代码块一次写全，含 `groupOrder`）」，并把它写进 `RUN:30` 的单集序列。

**缺口 G-3：groupOrder 少了 `voice auditions`**
- `SSG:291` 声明 **10 组**：`story planning / character cards / **voice auditions** / scene cards / prop cards / shot table / text storyboards / shot prompts / shot clips / final delivery`；`SSG:932` 复述同一套。
- `PROD:143-144` 给每集会话的只有 **9 组**（无 `voice auditions`）；`PROD:72` 的 `canvas_set_state` 代码块写的是「`groupOrder=[主会话]` 或 `[story skill 的**九个**分组]`」。
- 后果：① 若系列路径真做了试镜，节点进 `voice auditions` 却未被声明 ⇒ 该组排到最末（`SSG:291`「未声明的分组会排在末尾」），画布顺序乱；② 更实质的是——**它诚实反映了声线链路没被排进系列流程**（G-1 的同一根因）。
- 建议：要么补齐第 10 组，要么在 `PROD` 里明确「本片型不用 `voice auditions`」并把 G-1 的方案定为 `text-only`（那就得同步删掉 `SSG` 在系列路径的试镜承诺）。

**缺口 G-4：分镜模式从未被问**
- `SSG:578` 有独立分镜模式卡（单文本 / 单文本+铅笔图）；`PACK:170-183` 十项没有它，`PROD:48-61` 也没有 ⇒ 系列路径不问，AI 按默认「单文本」走。
- 后果：低（默认正是推荐项），但属「未声明即默认」；若某集需要可视化预演（高潮集），没有触发点。建议在 ⑥ 增加一行「分镜模式：单文本（默认）/ 可视化」，默认单文本。

**缺口 G-5：BGM 被当成不存在的能力，且没有任何门**
- `SSG:870`「**无 BGM**：注册表当前没有 `audio.music` 工作流，插件不能生成配乐」；`PROD:326`「（**插件不能生成 BGM**，必须后期贴）」；`PROD:353`「不生成 BGM」。
- 事实：插件已有 `audio.music` 能力（`lib/manifest.js:36`；工具 `comfy_generate_music` / `comfy_render(capability='audio.music')`，`lib/index.js:3943-3978`）。
- 后果：**配乐被当成纯人工后期活**，既没问过用户「要不要生成 BGM」（应是一张低成本决策卡），也没把「贴 BGM」计进任何人工触达统计；交付清单里只留一句「BGM 建议」（`SSG:899`）。
- 建议：交付阶段增加一项（或并入交付卡）：「BGM：`comfy_generate_music` 生成 / 原生无配乐 / 后期自贴」。

**缺口 G-6：每集交付没有人工验收卡（runbook 读法下）**
- `RUN:96-104` 的「拼接 + 交付」只有 `video_concat` → 终检 → 写交付清单 → 回写状态，**没有选项卡**；`PROD:244` 的 G-E 就是门 3 batch。
- 而 `SSG:926` 有交付批准卡，`PROD:234` 又说 STEP 5.5–8「完全照执行」⇒ 该卡到底存不存在取决于读法。
- 后果：量产 50–100 集时，「本集交付」与「本集片段批准」合并成一件事，**成片级验收（拼接后观感、清晰度跳变、混档、字幕混入）没有单独的人工确认点**。建议：保留一张极简「本集成片验收卡」（批准交付 / 重渲某镜 / 重拼），成本 1 次/集，换掉 runbook 里缺失的那一步。

### 5.3 最值得合并的 3 道门

1. **STEP 0 的 13 连问 → 1 张「生产规格卡」**（分 3 屏：① 创意 ② 成本 ③ 技术）

### 5.4 writer 的「每个阶段至少一组关键选项」vs 量产节奏

- writer 的强制约束：`WRI:577`「必须在整个创作流程中不停向用户确认…每个大阶段内部也要拆成若干小确认点」；`WRI:581` 六个高影响阶段都要确认；`WRI:609`「每个阶段至少提出 1 组关键选项，并**等待**用户确认或明确授权默认推进」。按 §2.3 计，从前置到 EP01 可用剧本 = **7 次**（G-W01…W07）。
- production 的节奏约束：`PROD:169-171`「前 10 集优先」+ `/episode 1-10` 批量 + `/review N` 每集；`PROD:173`「每批剧本批准，**不再重复问创作取向**」；`PROD:251`「一晚上 4–6 集」；`PROD:230`「**不许再向用户逐项问十项**」。
- **冲突点**：writer 的粒度是「每集一次生成前确认」（`WRI:257-259`）+「每集一次 /review」（`WRI:362`）；production 的粒度是「每批一次」。若整部量产走 writer，80 集 = 80 次 `/episode` 确认 + 最多 80 次 `/review`（`WRI` 说 review「可选」，但 `WRI:584` 与 `WRI:600` 又把「每集写完可跑自检」写成质量纪律）⇒ **剧本层就是 80–160 次人工触达，比成片层（6/集 × 80 = 480）小，但完全不在 production 的节奏模型里**。
- **冲突点 2**：`WRI:600` 的「18–25 句有效对白」与 `PACK:148` 的「14 句对白 / 台词 186 字 ≈47s」是两套口径（90s vs 120s、18–25 句 vs ≤对白镜数）——返工门：按 writer 写完的 120s 剧本进 production 会被压成 90s，`PROD:172` 说「每集只落到三件事」，压缩责任模糊。这属 task-1 的范围，此处只标注它**会在 G-B 造成返工确认**。
- **结论**：两者不能同时全开。建议在 G-S 时一次性锁定「剧本粒度」：**整部量产 ⇒ 每批 5–10 集一确认、/review 抽 20%**；**单片/样片 ⇒ 按 writer 原节奏每阶段追问**。否则 `PROD:230` 的「不许再问十项」只约束成片层，剧本层反而成了最大的人工门来源。

## 7. 给决策者的三句话

1. **单片路径的问题不是「门太多」，是「门都堆在最前面」**：13 张规格卡在任何产物之前，而真正随镜头数增长的只有门 3——把 STEP 0 合成 1 张卡（−11）+ 资产合成 1 张（−4），单片从 28 降到约 13（batch）/ 23（per-shot）；再把门 2/分镜/渲染参数三连合并（−2），约 11 / 21。
2. **连续短剧路径用「预填 + 禁止追问」换来了低触达（6/集），但预填表漏了「声线方案」这一项，而它恰好是 SSG 里唯一被写成「必须作答、不许 AI 默认」的硬门控**——结果是 50–100 集全部静默走 text-only，且交付清单不会记录这条风险（`SSG:239`/`307` 的承诺失效）。这是本次审计发现的**唯一「不问就付钱」级缺口**。
3. **`reviewMode` 与 `groupOrder` 属于「有值但没落地」**：值写在 `PROD:58/63/71-72`，落地动作却不在 `PROD:8.1` 的每集 SOP 里；一旦每集新会话按 SOP 走，`SSG:690` 读到空值 → 按 per-shot → 每集 6 门变 24 门。修法是一行：把 `canvas_set_state` 插进 §8.1。
