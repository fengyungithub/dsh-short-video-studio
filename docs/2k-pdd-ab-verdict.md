## ⚠️ 勘误（2026-09-23）：本文的 2.91× 结果**没有**落在当前上线的 `-ctx-balanced-pdd-2k` 上

本文 §2–§4 的 A/B 测的是**变体 A：PDD 只进二遍**，图结构见 §2：
`2 ─┬─→ 首遍 sampler（base 20 步，不动）`
`   └─→ 2a PDDAccApply ─→ RefineHandoff.model`、`9b PDDAccScheduler ─→ RefineHandoff.sigmas`。

**但落地时 `scripts/make-2k-template.mjs` 派生 `-ctx-balanced-pdd-2k` 的方式与 §2 不同：
PDD 被接在了首遍**（`node 10` 的 sigmas ← `2a`、guider ← `2a`），二遍则沿用普通
`BasicScheduler`（`node 9b`）与 base 模型。**两者运行的是完全不同的方案，本文的 2.91×
不能援引到当前 `-ctx-balanced-pdd-2k` 上。**

实测差异（2026-09-23，56 帧、seed 20260922、同 prompt）：

| | 上线 `-ctx-balanced-pdd-2k`（PDD 在**首遍**） | 本文变体 A（PDD 在**二遍**） |
|---|---|---|
| 全长 | **1189.7s** | 223.8s（本文 §4） |
| 二遍 | 与无 PDD 版**逐字节相同** ⇒ 无加速 | 292.0s → 100.5s = 2.91× |
| 画质 vs 无 PDD | 有效宽度 **1.00×**（无增益）、平坦区锐度 0.91×（更软）、**闪烁 +32%** | 持平且略优（§0） |

根因：2K 的开销几乎全在二遍（序列 ≈ 首遍 4×，注意力随 S 超线性 ⇒ 二遍占 55%–83%，
见 `docs/2k-acceleration-variants-analysis.md` §0）。把 PDD 加在便宜的首遍上，
**不可能有明显收益**，反而把 §1.4② 预警的「过冲 → 闪烁」实现在了首遍上。

**修正**：新增 `-ctx-quality-pdd2-2k`（ref2v / i2v 各一份）把本文的变体 A 真正落地 ——
首遍与 `-ctx-quality-2k` **逐字节相同**，只把二遍的 model/sigmas 换成 PDD 侧。
配套 A/B：`scripts/ab-2k-pass2-pdd.mjs`；画质对比：`scripts/analyze-2k-pair.py`。

**`-ctx-balanced-pdd-2k` 应当退场**（已标 `internal: true`：不进档位解析、不出现在 UI/技能选项，

既没有速度优势（实测更慢），又没有画质优势（有效宽度 1.00×、闪烁更差）。
真正该上线的是 `-ctx-quality-pdd2-2k`。眼判图：`e2e-out/2k-ab2/eye/`（`scripts/eye-crops.py` 生成）。

## 1. 事前验证：先证明「PDD 的二遍确实落在训练网格上」

**在做任何效果实验之前**必须先证这件事，否则 `on_off_grid='error'` 会在采样时报错，
或者更糟——静默地用一个不在训练分布上的 σ 序列。

`scripts/probe-pdd-sigmas.mjs`（不出片，秒级）：

```
PDD 训练网格 (nfe=8) = 1.0000, 0.9882, 0.9730, 0.9524, 0.9231, 0.8780, 0.8000, 0.6316, 0
PDD denoise=0.3     = 0.8000, 0.6316, 0            ← round(8×0.3)=2 block，正好是网格尾部
✓ denoise=0.3 的序列 == denoise=1.0 网格的尾部 3 点 ⇒ 确实在训练网格上
✓ Apply.sigmas == PDDAccScheduler(denoise=1.0)     ⇒ 调度器是忠实的网格生成器
base simple/6 步/denoise=0.3 = 0.8372, 0.8000, 0.7500, 0.6792, 0.5714, 0.3871, 0
```

**最关键的一行是最后那个对比**：base 二遍的 σ 起跑点是 **0.8372**，PDD 是 **0.8000**，比值 **0.96×**
——两条链的**起跑噪声几乎一致**。这一点如果不先量出来，整个 A/B 会被误解成
「PDD 用了不同的噪声窗口」，差异就归因不清了。

> 顺带纠正一个直觉错误：`denoise 0.3` 听起来像「从 σ=0.3 开始」，实际是 0.8372。
> 因为模型带 `SigmaShift(12, 3)`，σ 网格在高 σ 端极度压缩，所以「去掉后 30% 的步」只去掉了很小的 σ 区间。
> 这也是为什么不能用 `denoise` 的数值去推断二遍的改动幅度。

## 2. 变体 A 的图（为什么二遍要单独一个 sampler）

```
SigmaShift(2) ─┬─→ node 7 guider ─┐
               │                   ├─→ node 10 首遍采样（res_multistep + BasicScheduler 20 步）
               │   node 8 ─────────┘
               │
               └─→ PDDAccApply(2a) ─→ node 17 RefineHandoff.model
                                       ↑ node 8b (euler)  ← 二遍专用 sampler
                                       ↑ node 9b PDDAccScheduler(nfe=8, denoise=0.3)
```

两处设计决定：

1. **二遍另起 `8b = euler`**。PDD 训练配对 euler，而 base 首遍用 `res_multistep`。
   node 8 被首遍和 RefineHandoff 共用，若不拆开，「只换二遍」的隔离就不成立。
2. **`2a` 挂在 `2` 之后**（而不是替换 `2`）。首遍拿未打补丁的模型，二遍拿打过补丁的，
   两条分支在 `17` 汇合。代价是要同时持有两个 model 对象——实测**没有**引发显存问题（见 §5）。

生成器：`scripts/make-2k-template.mjs`（`ALL_SPECS` = 普通 2k + `-pdd` 派生），
清单：`scripts/make-h3-variants.mjs`。图是产物，改结构改脚本后重跑。

## 4. 耗时实测（56 帧 · 2688×1536 · A800）

`scripts/ab-2k-pdd.mjs`。ComfyUI 的执行缓存会跨 prompt 命中，这里**显式利用它做分解**：

| 臂 | 配置 | 种子 | 实测 | 缓存命中 |
|---|---|---|---|---|
| A | base 2k，冷跑 | 20260922 | **414.4s** | 无 node 10 ⇒ 首遍真跑了 |
| A2 | base 2k，冷跑（复现） | 20262922 | **416.1s** | 无 node 10 |
| B | pdd 2k，**首遍命中 A 的缓存** | 20260922 | **129.3s** | **有 node 10** ⇒ 首遍被复用 |
| B2 | pdd 2k，冷跑 | 20261922 | **494.2s** ← 异常值 | 无 node 10 |
| B3 | pdd 2k，冷跑（复现） | 20263922 | **223.8s** | 无 node 10 |

### 4.1 分解（自洽到秒）

```
首遍 P1       = B3 − B = 223.8 − 129.3           =  94.5s
base 每次评估 p2   （见下方联立）                    =  48.67s
PDD 每次评估 p2'   = (129.3 − D) / 2                =  50.25s   ← 与 p2 差 3%，同一量级
2K 解码+编码 D     （见下方联立）                    =  28.8s

验算 base ： 94.5 + 6×48.67 + 28.8 = 415.3s   （实测 414.4 / 416.1）
验算 PDD  ： 94.5 + 2×50.25 + 28.8 = 223.8s   （实测 223.8，分毫不差）
```

`p2` 与 `D` 由两个独立实测联立得到：

- 本次 A 臂：`P1 + 6·p2 + D = 415.3`
- 早前 `probe-2k.mjs` 的 56 帧 / 20+3 步同构跑：`P1 + 3·p2 + D = 269.3`（`docs/learned-latent-upscale-2k.md` §3）
- 相减 ⇒ `3·p2 = 146.0` ⇒ `p2 = 48.67s`，回代 ⇒ `D = 28.8s`
- 再用 `B3 − B = P1 = 94.5s` 独立定出首遍

**每次评估的耗时几乎相同（48.67 vs 50.25，+3%）**，正是理论预期：PDD 换的是 NFE，不是内核。

### 4.2 加速比

| | base | PDD | 加速 |
|---|---|---|---|
| 二遍段（56 帧） | 6 × 48.67 = **292.0s** | 2 × 50.25 = **100.5s** | **2.91×** |
| 全长（56 帧） | **415.3s** | **223.8s** | **1.86×** |
| 全长（124 帧） | **1671.2s** | **826.0s** | **2.02×** |

与理论预测的 1.6×–2.2× 吻合（落在区间中位）。**交付长度上加速比更高**（2.02× > 1.86×），
因为 PDD 缩短的那一段（2K 二遍，≈125k token 序列）随帧数的超线性比首遍更陡——见 §4.4。

### 4.4 交付长度（124 帧）实测

`node scripts/ab-2k-pdd.mjs --only B2 --frames 124 --seed 20260930` → **826.0s**，冷跑、编译清单、
无 OOM、显存峰值 17.3 GiB，成片 2688×1536 / 124 帧 / 5.17s / 带音轨。

用 §4.1 的分解式（`P1=94.5, p2=48.67, D=28.8`，56 帧口径）联立两条 124 帧方程：

```
base@124 : P1·f1 + 6·p2·f2 + D·fD = 1671.2
pdd @124 : P1·f1 + 2·p2·f2 + D·fD =  826.0
相减     : 4·p2·f2 = 845.2  ⇒  f2 = 4.34      ← 二遍每次评估在 124 帧上贵 4.34×
取 fD = 2.21（编码近似线性）  ⇒  f1 = 3.59      ← 首遍贵 3.59×
```

帧数只涨 2.21×，二遍涨 4.34×、首遍涨 3.59×，且 **2K 二遍比首遍更陡**——
这正是序列长度 125k vs 37.8k 下注意力开销的差别，也是为什么 PDD 在长片上更划算。

⚠️ 口径说明：base@124 的 **1671.2s 来自早前的 `probe-2k.mjs` v2（手改图，数学与编译清单一致）**，
不是编译清单直跑。该数字在本轮已被间接验证：用它在 56 帧口径上联立出的
`p2 = 48.67s / D = 28.8s`，回代后同时对上 A（414.4/416.1）与 B3（223.8，分毫不差）。
若要完全无争议，可再直跑一次编译版 base@124（约 28 分钟）。

### 4.3 B2 = 494.2s 这个异常值怎么排掉的

不能靠「另一个数更顺眼」就丢掉它。三条互不依赖的证据说明它是环境噪声（该 GPU 是共享的，
开跑时 79 GiB 里只有 38 GiB 空闲）：

1. **反证**：B2 隐含「首遍 = 494.2 − 129.3 = 365.0s」，与早前同构实测的首遍+解码+精修总时长
   269.3s（20+3 步）直接矛盾——首遍不可能比「首遍 + 3 次评估 + 解码」还长。
2. **复现**：B3 与 B2 同配置、仅换种子，得 223.8s，且与分解式**精确**对上（94.5+100.5+28.8）。
3. **显存侧无结构差异**：A2 峰值占用 7.9 GiB、B3 是 8.1 GiB。若真是「两个 model 分支共居导致
   显存不足→权重流式」，峰值占用不该几乎一样。

结论：**取 223.8s 为冷跑全长真值**，并把 B2 记为环境噪声（不做二次解释）。

### 5.1 差异归因（`scripts/analyze-ab-diff.py`）

两条片子差异到底长什么样，避免把「画质持平」当成「几乎没变」：

| 量 | 值 | 含义 |
|---|---|---|
| PSNR(A, B) | 35.57 dB | 同一镜头、同一运动，像素级差异 ~1% |
| \|A−B\| 均值 | 2.273 / 255 | |
| 差分能量按尺度 | >9px 尺度 RMS 3.393 ｜ <9px 尺度 RMS 2.255 | 细则尺度占 **30.6%** |
| 边缘区 vs 平坦区差异 | 2.786 vs 1.503（比 1.85） | 改动**集中在结构边缘**，不是全局明暗偏移 |

即：PDD 的二遍确实在**重绘细节**（三成能量在 <9px 尺度、且集中在边缘），

### 8.1 已知的会话可见性问题

新生成的清单**在正在运行的插件进程里看不到**（`workflow="…-2k-pdd"` 解析失败）：
`lib/index.js` 的注册表清单位于模块级缓存，本次已加 `manifestSignature()`
（按 `workflows/` 与用户目录的文件名+ mtime + 大小做键）在 `getRegistry()` 里自动重载——
但**正在运行的进程仍是旧模块**，要等插件重新加载（dsh 重启）才生效。
任何**新开的 node 进程**都能立刻看到这两份清单（本页所有实测都是这样跑的）。
